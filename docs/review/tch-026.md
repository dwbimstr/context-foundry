## Findings

1. **P1 — runtime and package mismatch.** [PR #9](https://github.com/dwbimstr/context-foundry/pull/9),
   head `8d5dda8d64f72bff2bff57dd2226d2ff5aca4a6e`, changed only the root
   Cargo manifest/lock from 0.24.0 to 0.26.0. `torch-sys::version_check` now requires
   2.13.0; a supported 2.11.0 installation cannot satisfy it. Independently,
   `scripts/package.sh --with-learning` explicitly refused any torch-sys other
   than 0.24.0 and emitted a 2.11.0 requirement. That package failure follows
   directly from the guard, even if compilation succeeds with a new runtime.
2. **P1 — the Python upgrade also needs its Rust consumer updated.**
   [PR #2](https://github.com/dwbimstr/context-foundry/pull/2), head
   `543683a2a825e5427dd1e5cfc2031bd9479ea5e5`, changes only
   `tools/feasibility/runtime-requirements.txt`. That separate crate pins tch
   0.24.0 in its own manifest/lock. Its documented decision-probe build uses
   `LIBTORCH_USE_PYTORCH=1`, so Python 2.13 alone violates its version check.
   Updating the root crate does not update this scratch crate. Existing captured
   results were produced with 2.11/0.24 and must remain labeled that way.
3. **P2 — default CI cannot validate this upgrade.** Neither default Cargo command
   enables `learning-worker`. The actual worker backend and checkpoint parity
   integration tests are additionally macOS-only. A successful Linux build of
   `foundry-learn` compiles its unsupported-platform entry point, not macOS serving.
   Linux does compile and execute the shared tensor model library when the feature
   is enabled. The new workflow makes that distinction explicit.

The [October 8 run](https://github.com/dwbimstr/context-foundry/actions/runs/37820717040)
ran the original PR head. Job `113460745206` failed on the unused macOS-only
`PERL_MEMORY` test constant. Job `113460744975` failed on missing tokenizer/config
fixtures and offline install-test dependency fetches (`bindgen`, `adler2`). These
were default-feature failures, not observed tch API, ABI or numerical failures.
Current main (`0d8dcca31024315bcfe6eaadbc8e27c5a457c401`) already contains their
platform guard, fixture-download and `cargo fetch --locked` corrections. This local
experimental branch rebases the dependency patch onto that main revision.

## Upstream evidence and compatible corrections

The published tch/torch-sys 0.26.0 crates identify upstream commit
[`4227b89b72059b0651ff83a38637693574e0a2d6`](https://github.com/LaurentMazare/tch-rs/tree/4227b89b72059b0651ff83a38637693574e0a2d6).
[`torch-sys/build.rs`](https://github.com/LaurentMazare/tch-rs/blob/4227b89b72059b0651ff83a38637693574e0a2d6/torch-sys/build.rs)
owns `TORCH_VERSION = "2.13.0"`, `version_check`, Python runtime detection and C++
linking. Cargo verified the published crate checksums in both lockfiles. No
`LIBTORCH_BYPASS_VERSION_CHECK` was used. Rust 1.90 is retained.

The official macOS archive's `libtorch_cpu.dylib` now has a load command for
`@rpath/libomp.dylib` and an `@loader_path` rpath. Its `libomp.dylib` still has the
absolute install ID `/opt/llvm-openmp/lib/libomp.dylib`, but the *consumer's load
command* no longer uses that path. `build.rs` therefore retains `$LIBTORCH/lib`
as an executable rpath and removes the 2.11-specific preload stub. This is verified
Mach-O archive inspection on Linux, not execution by dyld. The torch dylibs declare
arm64 and a macOS 14.0 minimum; no claim is made that this minimum changed from 2.11.

Root and feasibility Rust pins, the Python reproduction input, contributor/deployment
instructions and package metadata now agree on 0.26.0/2.13.0. The packager also refuses
an absent/mismatched `build-version` under the binary's discovered LibTorch rpath.
This checks supplied runtime metadata; it does not prove arbitrary prebuilt binaries'
provenance. Install tests cover the new metadata and old/missing version refusals.

`decision_model::net::tests::clipped_adamw_matches_the_pytorch_213_cpu_reference`
exercises Foundry's actual `Model::clip_and_step` with three small autograd updates,
norm clipping, moment accumulation, weight decay and a nonfinite-gradient refusal.
Expected values were obtained with Python torch 2.13.0+cpu
(`cf30153c4c131c8164ee7798e5022d810682e2cb`), CPU float32,
`torch.optim.AdamW(lr=1e-4, betas=(0.9,0.999), eps=1e-8, weight_decay=0.01,
foreach=False, fused=False)`, `clip_grad_norm_(max_norm=1)`, initial parameter
`[1,-2]`, and successive linear-loss gradients `[6,8]`, `[-1,2]`, `[0.1,-0.2]`.
The existing marker-mask and RoPE tests also execute real LibTorch operations.
These small fixtures do not establish ModernBERT/head or training-recipe parity.

Linux x86_64, Rust 1.90.0, four Cargo jobs, CPU only:

- Real LibTorch 2.13 CPU archive: marker mask, RoPE, and clipped AdamW/nonfinite
  regression tests passed (3 tests). The first two also passed with the 2.13 Python
  wheel runtime. Tests loaded through the recorded rpath, without `LD_LIBRARY_PATH`.
- All 145 feature-enabled library tests passed; all-target Clippy with
  `learning-worker` passed; `foundry-learn` built. The Linux binary is the
  unsupported-platform stub, as noted above. `readelf`/`ldd` confirmed that the
  numerical test executable resolves `libtorch_cpu`, `c10` and OpenMP from the
  selected archive's lib directory.
- Default-feature all-target Clippy and all 142 library tests passed. The full
  default integration suite was not rerun for this review.
- The separately locked feasibility `decision-probe` passed `cargo check --locked
  --features tch,pyo3 --bin decision-probe` on Rust 1.90 against the same archive.
  This is compilation, not a rerun of its model/reference experiments.
- Formatting, package shell syntax, workflow YAML/run-block syntax and repository
  Markdown links passed. The macOS-only install test changes were inspected but
  neither target-typechecked nor executed on Linux.

Reproduce the Rust checks with a verified archive, without a Python dependency:

```sh
export LIBTORCH=/absolute/path/to/libtorch
cargo +1.90.0 clippy --locked --features learning-worker --all-targets -- -D warnings
cargo +1.90.0 test --locked --features learning-worker --lib
cargo +1.90.0 build --locked --features learning-worker --bin foundry-learn
```

The added [optional-worker workflow](../../.github/workflows/learning-worker.yml)
pins those archives, checks Rust 1.90 with the feature, runs the weight-free numerical
tests, and builds the worker on Linux and macOS. On macOS it additionally loads the
real worker without DYLD path overrides, assembles a development package and runs
fixture-worker install/version-refusal checks. This workflow has **not** run on
GitHub or a macOS host during this review. It downloads no model weights and does
not enable learned routing.
