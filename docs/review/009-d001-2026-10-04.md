## (a) and (b): the serving limit

- Recipe: the bridge renders `query: ` / `passage: ` itself exactly once and calls the unchanged loader with `input_type` omitted and `max_length=2048` (not the loader's 4096). Tokens are counted with the artifact tokenizer, `truncation=False`, on the rendered string - the call `encode()` itself makes. This tokenizer adds **no special tokens** (`tokenizer.json` post_processor `special_tokens` is `{}`; `add_special_tokens` True/False both give 1 id; BOS/EOS exist but are never inserted), so overhead is just the prefix: 2 tokens for `query: `, 3 for `passage: ` (`logs/tokenizer_recipe.json`).
- (a) `texts/a_2048.txt` is exactly 2048 tokens including `passage: ` (`logs/fit.log`). Three separate sandboxed processes each encoded it: 2048-d, finite, norm ~1; a second call in the same process returned a bitwise-identical vector. Time and memory ranges above; `report.json` gives each run. The short-input runs (c, f) peak at 0.98 / 0.96 GiB footprint, so the 2048-token encode adds about 0.60 GiB; the MLX allocator peak was 1.32 GiB including 0.60 GiB of weights. Max RSS fluctuates between runs and under-reports unified memory; use footprint and the MLX peak.
- (b) `texts/b_2049.txt` is exactly 2049 tokens. The bridge counted it, refused it, and never called `encode`: 2.5 ms to decide and zero MLX allocation after the reset. Tokenizer-only sandbox runs (no weights loaded) give accept at 2048 / refuse at 2049 for both `passage` and `query`.
- Loader at 2049 (evidence only, not a serving path): with `max_length=4096` it encodes all 2049 tokens; with `max_length=2048` it drops the last token without raising or printing (kept 2048 of 2049; stderr between the phase markers is empty) and returns a valid vector that differs from the full-input vector (cosine 0.999981). The loader's silent truncation is exactly why the Foundry-side count-and-refuse check is needed.
- Missing artifact: the loader's `load()` sends any non-directory path to `huggingface_hub.snapshot_download`; the bridge guard fails by name first (`logs/missing_check.json`): 'artifact file missing: /private/tmp/cf-009-d001/texts/probe_missing/model.safetensors'; 'artifact directory missing: /private/tmp/cf-009-d001/texts/probe_absent'. ## (e) `apply_yarn_scaling` warning

- Reproduced in every run: `[transformers] Unrecognized keys in `rope_parameters` for 'rope_type'='yarn': {'apply_yarn_scaling'}`. It is emitted when `AutoTokenizer.from_pretrained(artifact_dir)` loads `config.json` (also in tokenizer-only runs), not by the model code.
- Source: config key `config.json:29` `rope_parameters.apply_yarn_scaling = false`; warning raised at `venv/lib/python3.12/site-packages/transformers/modeling_rope_utils.py:1118` (`_check_received_keys`, 1091-1118) because `_validate_yarn_rope_parameters` (931-941) accepts only `rope_type, factor, original_max_position_embeddings` plus optional `rope_theta, attention_factor, beta_fast, beta_slow, mscale, mscale_all_dim, truncate`. It is a schema warning, not a failure.
- MLX: `mlx_lm/models/rope_utils.py:235-281` `initialize_rope` builds `YarnRoPE` (class at :128) from `factor` and `original_max_position_embeddings, beta_fast, beta_slow, mscale, mscale_all_dim` (263-273); `apply_yarn_scaling` is never read - measured: freqs identical with the key set true or removed. So **MLX ignores the key and applies YaRN** (factor 16, original 16384): 21 of 64 frequency pairs unchanged, 27 slowed 16x, 16 partial, at every length including <= 2048. YaRN's magnitude scale is 1.0 (no q/k magnitude change). The loader's llama_4 position scale is exactly 1.0 at every position below 16384 (measured for 2048 and 2049), so it is a no-op for inputs of 2048 and 2049 tokens.
- Open point at first pass: whether upstream means YaRN to be disabled (`false`) could not be settled offline. Sensitivity with only the rope constructor swapped for plain RoPE: cosine 0.99998 (10 tok) ... 0.99714 (2048 tok). Settled 2026-10-04 by the reference comparison below: the torch reference also applies YaRN and matches MLX-with-YaRN better.

## (g) admission

Design (`logs/g_admission.json`, repeated in `g_admission_r2.json`): worker threads call the unchanged loader through PyO3. A is a 2048-token encode that the "client" abandons 100 ms after it starts (no cancel API exists); B is a short query requested right after.

- A timed-out call keeps running: A finished 887.3 / 1589.2 ms after the simulated timeout (runs 1 / 2).
- Calls are not serialized: B entered Python 0.1 ms after it was requested while A was still executing, and both ran; B finished 720.7 / 1552.2 ms after its request versus 34.6 / 102.6 ms solo, and 167 / 37 ms before A finished, so its latency was set by A's remaining work on the shared GPU queue. Against the 1500 ms query ceiling that was over it in 1 of 2 runs. [inference] MLX evaluation releases the GIL, so A does not hold it for its whole call.
- No queue limit, busy refusal or cancellation exists in the loader or PyO3. A worker-held atomic slot (scratch code, not a product mechanism) refused B at 0 ms, before any work, and stayed held until A truly finished (847.8 / 1418.2 ms after the client gave up). A client-side semaphore would have released at the timeout while A kept executing for another 887.3 / 1589.2 ms (unguarded runs). Stopping abandoned work needs process termination, which was not exercised.
